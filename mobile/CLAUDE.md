# 대피 안내 앱 (fireapp)

시각장애인이 화재 시 **진동과 소리만으로** 대피하도록 돕는 iOS 앱.
평소에는 건물의 피난안내도를 모으는 촬영 앱으로 쓰인다.

관련 프로젝트: `../fire` — 웹 버전(PWA) + 백엔드(Express) + 경로탐색(`shared/`).
이 앱은 그 백엔드와 이을 수 있게 설계됐지만 **아직 연결돼 있지 않다**(아래 참조).

---

## 실행

```bash
npm install
npx expo start --lan --port 8081
```

아이폰에서 **Expo Go** 앱으로 `exp://<맥IP>:8081` 접속. Xcode 불필요.

```bash
# 번들이 깨지지 않았는지 확인 (JSX 때문에 acorn 은 못 쓴다)
curl -s "http://localhost:8081/App.js.bundle?platform=ios&dev=true" -o /dev/null -w "%{http_code}\n"
```

## 화면 구조

메뉴도 탭도 없다. **화면 하나가 상황에 따라 바뀐다.**

```
평소       CaptureScreen   피난안내도 촬영
  ↓        ReviewScreen    찍은 사진 확인 (손가락·반사광은 찍은 뒤에만 안다)
  ↓        SubmitScreen    가로 폭·방위 입력 → 서버로 (AI 판독까지 한 번에)
화재 감지  AlarmScreen     전체를 덮음 (사이렌·진동·음성·손전등)
확인 후    (위치 자동 판정) 비콘이 알려준다 — **묻지 않는다**
  ↓        GuideScreen     서버 경로를 진동·소리로 (구간마다 끊어서)
  └ 예외    StartScreen     비콘까지 실패했을 때만 물어본다
```

**도면·경로는 이 앱이 만들지 않는다.** `../fire` 백엔드가 짜서 준다.
다만 **서버에 못 닿으면 멈추지 않는다** — 도면이 없으면 `demoPlan.js`,
경로를 못 받으면 `pathfinding.js` 로 잇는다. 닿을 때는 언제나 서버가 정답이고,
폴백으로 돌 때는 음성·화면으로 그 사실을 **반드시 알린다.**

**대피 안내는 사용자가 여는 게 아니라 스스로 열린다.** 시각장애인이 화재 중에
메뉴를 찾아 들어갈 수 없기 때문이다. `App.js` 의 `phase` 가 이 전환을 관리한다.

## 반드시 알아야 할 물리적 제약

### 폰에는 진동 모터가 하나뿐이다

"왼쪽만 진동" 같은 건 **물리적으로 불가능하다.** 폰은 단단한 한 덩어리라
모터가 어디 있든 전체가 떨린다. 그래서 방향을 **공간이 아니라 시간축**에 담는다
— 사용자가 폰을 돌리면 맞는 쪽에서 신호가 세진다(아이폰 '나의 찾기'와 같은 원리).

방향을 찾는 건 결국 **사용자의 팔**이고, 폰은 "맞다/틀리다"만 답한다.
햅틱 벨트(모터 16개)처럼 방향 자체를 주려면 별도 하드웨어가 필요하다.

### 그래서 소리가 방향을, 진동이 세기를 맡는다

| 채널 | 전달하는 것 | 이유 |
|---|---|---|
| 소리 | **방향** (스테레오 좌우) | 폰으로 방향을 줄 수 있는 유일한 수단 |
| 진동 | **세기** (얼마나 맞는가) | 시끄러워도 전달된다 |

골전도 이어폰을 전제한다 — 귀를 막지 않아 화재경보·사람 목소리를 함께 들을 수 있다.

### Expo Go 는 진동 세기를 5단계로만 준다

`expo-haptics` 는 미리 정해진 5단계(Soft·Light·Medium·Rigid·Heavy)뿐이다.
연속 세기(0~1)는 네이티브 모듈이 필요하고 Expo Go 에서 안 돌아간다.

**그래서 진폭과 빈도를 곱해 쓴다** — 사람이 느끼는 세기는 진폭만이 아니라
단위 시간당 자극량이다(금속탐지기가 빠르기로 강약을 만드는 원리).
정면 근처에서는 간격을 바닥까지 좁혀 **끊기지 않는 느낌**을 만든다.

네이티브로 올릴 때는 `src/haptics.js` 의 `setEngine()` 에 연속 진동 구현을
꽂으면 되고 **나머지 코드는 그대로다.**

## 위치는 묻지 않는다 — 비콘이 알아낸다

`StartScreen`("지금 계신 곳은?")은 **예외 경로다.** 불이 난 상황에 시각장애인에게
강의실 13개를 하나씩 넘겨보라는 건 말이 안 된다. 정상 흐름은 비콘이 위치를
판정하고 곧바로 안내로 넘어가는 것이고, 이 화면은 그마저 실패했을 때만 뜬다.

### 왜 삼각측량이 아닌가

RSSI 를 거리로 환산하면 실내 반사·인체 감쇠로 3~5m 씩 틀린다. 하지만
**"어느 비콘이 제일 가까운가"라는 비교**는 그 오차에 견딘다. 대피 안내에
필요한 해상도는 지점 단위("302호 앞")이고, 최근접 판정이 정확히 그 해상도다.

| 처리 | 값 | 이유 |
|---|---|---|
| 이동평균 | 3초 | 원시 RSSI 는 가만히 서 있어도 ±10dB 튄다 |
| 전환 문턱 | 5dB | 이만큼 더 세지 않으면 도전 자격 없음 |
| 유지 시간 | 2초 | 없으면 지점 경계에서 위치가 초 단위로 깜빡인다 |
| 비인접 전환 | 유지시간 ×2 | 통로로 안 이어진 곳으로의 "이동"은 대개 반사가 만든 허상 |
| 확정 못 하면 | `null` | 아무 지점이나 돌려주면 엉뚱한 경로가 나온다 |

### 지금은 시뮬레이션이다

BLE 스캔은 **Expo Go 에서 안 된다**(`react-native-ble-plx` + 개발 빌드 필요).
그래서 `beaconSim.js` 가 도면 좌표에서 신호를 만든다 — 실측 수준의 노이즈(±6dB)와
패킷 유실(15%)까지 섞으므로 `BeaconLocator` 는 그게 가짜인지 모른다.

**노이즈를 줄이지 말 것.** 시뮬레이션에서만 통과하는 측위는 현장에서 처음
실패하고, 그때는 원인이 노이즈인지 로직인지 가릴 수 없다.

비콘 id 가 없는 도면은 지점마다 `SIM-<id>` 가상 비콘이 있다고 보고 돈다.
실제로 달기 전에 "달면 이렇게 된다"를 보여줄 수 있어야 설치 여부를 판단할 수 있다.

**실기기 전환 시 바뀌는 곳은 `beaconLocator.js` 의 `scanOnce()` 하나뿐이다.**

## 아직 검증되지 않은 가장 큰 위험

**실내 나침반이 쓸 만한지 모른다.** 철골·전선·엘리베이터가 자기장을 휘게 한다.
이게 안 되면 방향 안내 접근 자체가 성립하지 않는다.

그래서 `BearingSensor.stability` 로 흔들림을 재고, 기준 이하면 **안내를 멈추고
경고한다**(`GuideScreen` 의 `STABILITY_FLOOR`). 틀린 방향을 자신 있게 알려주는
것은 아무것도 안 하는 것보다 위험하다. 이 안전장치는 어떤 개선을 하더라도 유지할 것.

### `fire/shared/` 에서 내려오는 사본 — **여기서 고치지 말 것**

아래는 `../fire/shared/` 가 원본이고 `npm run sync:app`(fire 쪽에서) 으로 복사된다.
앱에서 고치면 다음 동기화에 덮인다. 원본을 고치고 다시 돌릴 것.

| 파일 | 역할 |
|---|---|
| `src/floor-plan.js` | 도면 모델. 판단 계층이 쓰는 기하 계산(`edgeSteps`, `trueBearing`) |
| `src/fusion.js` | **판단 계층.** 확정·이동·참고를 하나의 위치·확신도로 |
| `src/beacon-anchor.js` | 비콘 판정 → 판단 계층 |
| `src/altitude.js` | 기압 → 층 이동(엘리베이터/계단 구분) |
| `src/altitude-anchor.js` | 층 이동 → 판단 계층 |
| `src/magnetic.js` | 지자기 지문 대조 + 재현성 판정 |
| `src/magnetic-anchor.js` | 지자기 → 판단 계층 (감점 + 누적 확정) |

`positioning.js` 와 `pathfinding.js` 는 **이미 손으로 갈라진 상태**라 동기화 대상이
아니다(메서드 이름부터 다르다: `setPlan` vs `setFloorPlan`). 합치는 일은 따로 해야 한다.

## 서버와의 경계

**앱은 계산하지 않는다.** 판단을 두 곳에 두면 관제 화면과 앱이 다른 말을 하게 되고,
대피 중에 그건 치명적이다.

| | 누가 |
|---|---|
| 어느 출구로 갈지, 어느 통로를 지날지 | **서버** (`shared/pathfinding.js`) |
| 위험 구간 제외, 화재 판정 | **서버** |
| "지금 이쪽, 몇 걸음" → 진동·소리 | **앱** |
| 걸음 세기, 방향 맞추기 | **앱** |

```
GET  /api/positions            내 위치 (비콘 게이트웨이·관제가 올린 값)
POST /api/plans/draft          찍은 도면 접수 → AI 판독 → 초안 (확인 전이라 안내엔 안 쓰임)
GET  /api/map                  활성 도면 (노드·통로·축척·northOffset)
POST /api/route {from, kind}   경로. route: null 이면 안전한 길이 없다는 뜻
GET  /api/hazards              3초마다 확인 → 가던 길에 불이 붙으면 재탐색
POST /api/sos                  안내를 멈출 때 보호자·관제에 알림
```

서버 주소는 **Expo 개발 서버가 떠 있는 곳**에서 알아낸다(`src/serverUrl.js`).
맥 IP 를 코드에 적으면 DHCP 로 바뀔 때마다 폰에서 "요청 시간 초과"만 뜬다
(이 프로젝트에서 두 번 겪었다). 배포 시에는 `EXPO_PUBLIC_FIRE_SERVER` 로 못박는다.

### 방위에는 두 종류가 있다

```
도면 방위   도면 위쪽이 0.  도면 안에서만 참
실제 방위   자북이 0.       나침반과 견줄 수 있다
```

둘을 잇는 값이 도면의 **`northOffset`**(도면 위쪽이 실제 몇 도인가)이다.
도면은 종이에 아무 방향으로나 그려지므로 위쪽이 북쪽이라는 보장이 전혀 없다.

- `northOffset` 이 **없으면 진동 방향 안내를 끈다.** 추측해서 가리키지 않는다.
- **좌우 회전 안내는 보정 없이도 맞다** — 이전 구간과의 *차이*라서 상쇄되기 때문이다.
  그래서 보정이 없는 도면에서도 안내가 아예 죽지는 않게 나눠 두었다.

편집기(`../fire/architect.html`)의 "도면 위쪽이 향하는 실제 방위"에서 넣는다.
빈 칸과 0(북)은 **다른 값**이다 — 모르는 걸 0으로 저장하면 앱이 자신 있게 엉뚱한 쪽을 가리킨다.

### 온도 센서는 규격만 있다

센서를 아직 안 달았으므로 **앱이 받을 형태만** 정의했다(`src/fireServer.js`).
센서를 달면 서버가 아래를 하면 되고 **앱은 고칠 게 없다.**

```
센서 게이트웨이 → POST /api/sensors/temperature  {sensorId, edgeId, celsius}
서버가 임계값 판정 → /api/hazards 에 화재 표시
앱이 그걸 받아 AlarmScreen 전환
```

**임계값 판정은 서버에 둔다.** 기준이 바뀌어도 앱을 다시 배포하지 않아도 되고,
관제 화면과 판단이 어긋나지 않는다.

## 접근성 규칙

### VoiceOver 를 대체하지 말고 활용한다

시각장애인은 VoiceOver 를 **항상 켜두고** 쓴다. 우리가 읽어주는 기능을 만들 게
아니라, VoiceOver 가 제대로 읽도록 `accessibilityLabel` 을 붙인다.

다만 VoiceOver 는 **손가락으로 짚어야 읽는다.** 대피 중에는 화면을 더듬을 수
없으므로 `AccessibilityInfo.announceForAccessibility()` 로 **먼저 말을 건다.**

### 상태가 바뀔 때만 말한다

계속 떠들면 아무도 안 듣고, 무엇보다 **주변 소리를 덮는다.** 시각장애인에게
화재경보·사람 목소리·지팡이 소리는 시야에 해당한다. 그걸 가리는 안내는 위험하다.

- 정렬 힌트: 힌트 문구가 바뀔 때만
- 정면 진입/이탈: 상태가 뒤집힐 때만
- 상황 요약: 30초에 한 번

**연속 배경음을 추가하지 말 것.**

### 화면은 두 사용자를 함께 섬긴다

큰 화살표·거리 표시는 **눈이 보이는 동행자**(소방관·가족)와 저시력자를 위한
것이다. 시각장애인에게는 같은 정보가 진동·소리로 간다. 하나를 지우지 말고
**이중화를 유지할 것.**

## 촬영 화면 설계

신분증 촬영 UX 를 따랐다 — 사각 틀, 맞으면 초록 테두리 + 확인음.
다른 앱에서 익힌 동작이라 설명 없이도 통한다.

**왜 똑바로 찍어야 하나**: 비스듬하면 도면이 사다리꼴로 일그러져 **축척이
위치마다 달라진다.** 그러면 "9걸음"이 어디선 7걸음이 되고, 시각장애인은
그 걸음 수를 믿고 걷기 때문에 곧 오안내가 된다.

**롤(좌우 기울기)을 가장 엄하게 본다** — 회전은 모든 좌표를 틀어버리고
나중에 보정하기도 어렵다. 위아래 각도는 상대적으로 관대하다.

### 갤러리 검증의 순환 문제

"대피도인지 판별"하려면 AI 가 필요한데 **그 AI 를 학습시키려고 사진을 모으는
중**이다. 엄격하면 데이터가 안 쌓인다.

그래서 명백히 아닌 것만 거칠게 걸러내고(`looksLikePlan`), 애매하면 사용자에게
묻는다. 판별 모델이 생기면 이 함수만 교체하면 된다.

---

## 하지 말아야 할 것

- **연속 배경음 추가** — 주변 소리를 덮는다
- **안정도 검사 제거** — 틀린 방향을 자신 있게 알려주게 된다
- **각도로 안내** ("30도 우회전") — 사람은 각도를 못 잰다. 벽·촉각 기준을 쓸 것
- **진동 횟수를 늘려 정보를 더 담기** — 위급 상황에서 세는 건 실패한다
- **화면 없이 진동만으로 설계** — 동행자·저시력자가 못 본다

## 현재 상태

동작 확인됨(실서버 대조): 도면 수신 → 경로 요청 → 구간별 방위·걸음 계산 →
좌우 회전 판정 → 가던 길에 불이 붙으면 재탐색(0.07ms). 촬영 정렬 판정,
화재 경보(사이렌·진동·음성 3회·손전등), 시작 위치 음성 선택.

**미검증 — 여기서 막히면 나머지가 다 소용없다:**
- 실내 나침반이 철골·배전반 옆에서 버티는지
- 5단계 진동으로 "가까워진다"가 느껴지는지
- 한 손에 지팡이, 한 손에 폰으로 실제로 걸을 수 있는지
- 걸음 감지 임계값(`PEAK_THRESHOLD`)이 지팡이 짚는 걸음에도 맞는지

**방위는 촬영 직후에만 잴 수 있다.** 도면이 실제로 어느 쪽을 향하는지는 그 앞에
서 있는 사람만 안다. 그래서 `SubmitScreen` 이 나침반으로 직접 재고, 나중에
편집기에서 채우게 미루지 않는다.

미구현: 화점→도면 좌표 대응(그래서 실제 신호에서는 화점 회피가 안 된다),
온도 센서 하드웨어, 건물·층 여러 개(활성 도면이 하나뿐), 서버 영구 저장(Firestore
키 미설정), 촬영 사진 서버 업로드, 2D→3D 도면 렌더링.
