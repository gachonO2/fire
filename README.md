# SAFEXIT — 시각장애인 실내 대피 AI 내비게이션

> 재난 때 '가까운 출구'를 알려주는 것이 아니라, 시각장애인이 **현재 위치에서 연기·열·장애물을 피해
> 실제로 이동할 수 있는 경로**를 음성·진동으로 안내한다.

대상 건물은 **AI공학관**(지상 7층 + 옥탑). 6층 COCONE 구역이 실측·답사가 끝난 기준 층이고,
나머지 층은 도면을 올린 만큼만 켜진다.

목표는 "완전 자율 대피"가 아니라 **접근 가능한 동적 경로 + 안내 UX 검증**이다.

## 1. 문제 정의와 사용자 분석

### 핵심 문제

기존 대피 안내는 **"가장 가까운 출구"** 를 알려준다. 그런데 화재 때 필요한 것은 가까운 출구가
아니라 **지금 갈 수 있는 출구**다. 가장 가까운 비상구가 연기로 막혀 있으면 그 안내는 사람을
불 쪽으로 보낸다.

시각장애인에게는 문제가 하나 더 있다. 대피 안내도, 유도등, 비상구 표지판이 **전부 시각 정보**다.
정전으로 조명이 꺼지고 연기가 차면 비장애인도 시야를 잃지만, 시각장애인은 **처음부터 그 정보에
접근할 수 없다.**

### 사용자 특성과 불편 요소

| 사용자 | 상황 | 불편 요소 | 설계 대응 |
|---|---|---|---|
| 시각장애인 (주 사용자) | 건물 안, 화재경보 발생 | "지금 어디인가"를 스스로 알 수 없다 | 비콘 측위로 위치를 **묻지 않는다** |
| | | 목록에서 자기 방을 찾는 데 스크린리더로 수십 번의 탭 | 판정 결과를 aria-live 로 즉시 읽어줌 |
| | | 시각 안내(유도등·표지판) 접근 불가 | 음성 + 진동 6개 명령으로 대체 |
| | | 방향이 맞는지 확인할 방법이 없어 발을 못 뗀다 | 방향 확인 모드 (좌우 스테레오 + 진동) |
| | | 계속 나오는 안내음이 화재경보·사람 목소리를 덮는다 | 누르고 있는 동안만 신호 |
| 보호자 | 건물 밖, 연락이 안 됨 | 대상자가 어디 있는지, 나왔는지 알 수 없다 | 공유 코드로 위치·경로·현재 안내 실시간 확인 |
| 관제·안전요원 | 방재실 | 어느 층 어느 통로가 막혔는지 한눈에 안 보인다 | 층 스택 + 3D 모형 + 실시간 위치 |
| 건축 담당자 | 도면 등록 | 층마다 지점·통로를 손으로 찍으면 10분 이상 | 사진 한 장 → AI 판독 → 확인만 |

### 설계에서 반복해 되돌아온 실패

**화면이 모르는 것을 아는 척하는 것.** 이 프로젝트에서 가장 위험한 실패는 안내를 못 하는 것이
아니라, 틀린 안내를 자신 있게 하는 것이다.

- 도면이 없으면 시연용 "병원 3층"을 채웠다 → 앱이 있지도 않은 복도를 안내했다.
  지금은 도면이 없으면 **없다고 말하고 안내하지 않는다.**
- 비콘이 없는 층에서 가상 비콘 62개가 파동을 냈다 → 화면은 예순두 대가 울고 있다고 말했다.
  지금은 **등록된 비콘이 없으면 아무것도 울리지 않는다.**
- 도면 없는 층을 "정상"으로 칠했다 → 아무것도 안 보면서 보고 있다고 말했다.
  지금은 **"도면 없음"으로 회색이다.**
- 게이트웨이가 이미지를 버려도 모델이 그럴듯한 도면을 지어냈다.
  지금은 **시야 점검이 먼저 돌고, 못 보면 판독을 시작하지 않는다.**

축척이 추정값이면 `scaleEstimated: true` 로 표시하고, AI 초안은 사람이 확인해야 활성화된다.
**빠뜨린 것은 사람이 채우면 되지만, 잘못 만들어낸 것은 사람이 알아채기 어렵다.**

### 범위 밖

당사자 실증, 공식 안전규칙 인증, 실제 위치 인프라 구축은 이번 범위가 아니다.
모의 데이터와 시뮬레이션으로 대체했고, 실제 연동 경로만 열어 두었다.

## 2. 기술 스택 선정

| 계층 | 선택 | 이유 |
|---|---|---|
| 프론트엔드 | **순수 JS (PWA)** — 빌드 도구 없음 | 오프라인 동작이 요구사항이라 서비스워커가 필수. 프레임워크를 얹으면 번들 없이는 못 도는데, 대피 앱은 네트워크 없이 열려야 한다 |
| 모바일 | **Expo (React Native)** | Web Bluetooth 스캔이 iOS 에 없고 안드로이드도 플래그 뒤에 있다. 실제 BLE 수신은 네이티브가 필요 |
| 백엔드 | **Node.js + Express** | 경로탐색 코드를 프론트와 **그대로 공유**하려면 같은 언어여야 한다 (`shared/`) |
| 데이터베이스 | **Firestore** (없으면 인메모리) | 실시간 변경 구독(onSnapshot)이 SSE 브로드캐스트와 맞물린다. 설정이 없으면 인메모리로 떠서 시연이 막히지 않는다 |
| 실시간 | **SSE** (WebSocket 아님) | 서버→클라이언트 단방향이면 충분하고, 재연결이 브라우저 기본 동작이라 프록시·방화벽 환경에서 안정적 |
| AI (도면 판독) | **YOLO 자체 학습 + Gemini/Claude** | 좌표는 탐지기가, 이름·연결은 언어모델이. 한쪽만 있어도 동작 |
| AI 서버 | **FastAPI (Python)** | YOLO 추론은 파이썬 생태계. 별도 프로세스라 꺼져 있어도 본체가 안 죽는다 |
| 배포 | **Firebase Hosting + Cloud Run** | 정적 프론트와 API 를 분리하되 `/api/**` rewrite 로 같은 출처 유지 |
| 테스트 | **Node 내장 실행 (의존성 없음)** | 테스트 러너를 안 쓰는 이유는 설치 없이 어디서나 `node test/x.mjs` 로 돌아야 하기 때문 |

### 왜 프레임워크를 안 썼는가

대피 안내는 **네트워크가 끊긴 상태가 정상 시나리오**다. 서비스워커로 캐시한 정적 파일만으로
경로 계산까지 되어야 하는데, 빌드 산출물에 의존하면 그 경로가 복잡해진다.
화면 수가 6개라 프레임워크의 이득보다 제약이 컸다.

### 사용자 시나리오

**시나리오 A — 대피 (주 시나리오)**

1. 사용자가 앱을 연다. **아무것도 누르지 않는다.**
2. 비콘이 현재 지점을 판정하고, 확정되면 "현재 위치는 601호 앞입니다" 음성이 나간다.
3. 대피 시작을 누른다. 긴 진동 1회 + "대피 모드를 시작합니다. 목표는 서편 비상계단입니다."
4. 걸으면 걸음이 감지되고, 구간이 끝날 때마다 다음 명령이 나간다.
5. 관제가 전방 통로에 화재를 표시하면 2초 이내에 재탐색하고 "위험" 진동 3회 + 새 경로.
6. 방향이 헷갈리면 방향 확인 버튼을 **누르고 있는 동안** 좌우 신호가 나온다.
7. 비상구에 닿아도 끝이 아니다. 계단으로 1층까지 내려가 밖으로 나가야 완료다.

**시나리오 B — 갈 곳이 없을 때**

모든 출구가 막히거나 위치 확신도가 40% 아래로 떨어지면, **임의로 안내하지 않는다.**
그 자리에 멈추게 하고 구조요청을 보낸다. 보호자와 관제 화면에 위치가 뜬다.

**시나리오 C — 도면 등록**

건축 담당자가 앱으로 피난안내도를 찍고 가로 폭과 방위를 넣는다. 서버가 사진을 저장하고
AI 로 판독해 초안을 만든다. 편집기에서 사람이 확인하고 저장해야 안내에 쓰인다.

**시나리오 D — 답사**

폰으로 답사 화면을 열고 그 층을 한 바퀴 걷는다. 비콘 지도와 지자기 지문이 자동으로 만들어진다.

## 4. 서비스 아키텍처 설계

```
┌───────────────────────┐        ┌──────────────────────────┐       ┌───────────┐
│ frontend/ (PWA)       │  REST  │ backend/ (Node+Express)   │ Admin │ Firestore │
│  · 사용자 앱          │ ─────▶ │  · 경로 계산 (권위)       │  SDK  │  hazards  │
│  · 관제 대시보드      │        │  · 위험 검증·인증         │ ────▶ │  sos      │
│  · 보호자 화면        │ ◀───── │  · 감지기·수신기 웹훅     │       │  positions│
│  · 도면 편집기·답사   │  SSE   │  · SSE 브로드캐스트       │       │  metrics  │
└───────────────────────┘        └──────────────────────────┘       └───────────┘
        ▲                                    ▲
        │                                    │
┌───────┴───────────┐          └──── shared/ (도면·경로·측위·감지) ────┘
│ mobile/ (Expo)    │                        │
│  실제 BLE 스캔    │ ───────────────────────┘
│  답사·촬영·안내   │
└───────────────────┘
```

### 기능 간 상호작용

```
관제가 통로 클릭
   → PUT /api/hazards/:edgeId
      → 저장소 변경
         → events 허브
            → SSE 브로드캐스트 (모든 화면)
               → 사용자 앱: 위험 변경 감지 → POST /api/route (재탐색)
                  → 음성·진동 안내 + 지도 갱신
                  → PUT /api/positions/:userId (상태 보고)
                     → 상태 전이면 보호자 알림 생성 → SSE → 보호자 화면 배너
```

온도 판독은 같은 흐름을 **자동으로** 탄다. `POST /api/sensors/temperature` 로 들어온 값이
임계를 넘으면 경로 계산 시점에 위험으로 변환되고, 위와 동일하게 전파된다.

### 설계 결정 세 가지

**1. 경로 계산의 권위는 서버에 둔다.** 클라이언트가 각자 계산하면 같은 상황에서 사람마다
다른 안내를 받는다. 다만 통신이 끊기면 프론트가 캐시로 직접 계산한다 — 그때는 화면에
"오프라인"으로 표시한다.

**2. `shared/` 가 단일 진실 소스다.** 도면·경로탐색·측위·감지 로직을 백엔드·프론트·모바일이
그대로 공유한다 (`npm run sync` → `frontend/shared/`, `npm run sync:app` → `mobile/src/`).
복제하면 임계값 기준이 갈라진다.

**3. 프론트엔드는 DB 에 직접 접근하지 않는다.** 모든 접근은 백엔드가 서비스 계정으로 한다.
브라우저에 자격증명이 노출되지 않고, 위험 상태 쓰기를 인증으로 통제할 수 있다.

### 측위 계층 — 신호 하나로는 안 된다

비콘 하나로는 층을 모르고, 기압 하나로는 어느 방인지 모른다. **판단 계층**(`fusion.js`)이
세 앵커를 확신도와 함께 합친다.

| 앵커 | 무엇을 아는가 | 모듈 |
|---|---|---|
| 비콘 | 어느 지점 앞인가 | `beacon-anchor.js` · `positioning.js` |
| 기압 | 몇 층인가 (계단·엘리베이터 이동) | `altitude-anchor.js` · `altitude.js` |
| 지자기 | 어느 통로인가 (자기장 세기의 순서) | `magnetic-anchor.js` · `magnetic.js` |

신호가 끊긴 구간은 걸음·방위(`step-detect.js` · `north.js`)로 잇는다.

**왜 RSSI 삼각측량이 아닌가.** 거리로 환산하면 실내 반사·인체 감쇠로 3~5m 틀린다. 하지만
"어느 비콘이 제일 가까운가"라는 **비교**는 그 오차에 견딘다. 필요한 해상도는 노드 단위
("601호 앞")이고 최근접 판정이 정확히 그 해상도다.

반드시 들어가는 처리 셋:

- **스무딩** — 원시 RSSI 는 정지 상태에서도 ±10dBm 튄다. 3초 이동평균
- **히스테리시스** — 새 비콘이 5dB 이상 세게 2초 지속돼야 전환. 없으면 경계에서 경로가 깜빡인다
- **그래프 제약** — 엣지로 이어지지 않은 노드로의 순간이동은 무시 (다중경로 반사가 만든 허상)

검토 후 배제: Wi-Fi RTT(iOS 미지원, 유선 AP 라 정전 시 사망), 삼각측량(3~10m 오차),
핑거프린팅(사전 측정 노동집약), UWB(앵커 고가·웹 API 없음).

### 화재 감지 계층

온도 숫자 하나로는 부족했다. 실제 건물 설비와 세 가지가 달랐다.

1. **연기감지기가 없었다.** 실제로 제일 많이 달리는 것이 연기감지기고, 불이 나면 연기가 먼저 운다.
2. **한 번 넘으면 바로 화재였다.** 실제 수신기는 예비경보로 잡아 두고 지속돼야 확정한다(축적).
3. **간격이 실제 기준과 달랐다.** 한 층에 52대는 실제 건물이 아니다. 국내 기준 간격으로 배치한다.

불은 점이 아니라 번진다 — `hazard-spread.js` 가 시간에 따라 반경을 넓힌다.

**온도 임계값**

| 판정 | 기준 | 경로탐색 반영 |
|---|---|---|
| 정상 | 45°C 미만 | 그대로 |
| 주의 | 45°C 이상 | 통행 가능하되 가중치 4배 (강하게 회피) |
| 통행 불가 | 60°C 이상 | 그 통로를 아예 뺀다 |
| 판독 끊김 | 60초 무갱신 | 신뢰하지 않음 (관제 화면에 표시) |

지점(교차점) 센서가 과열되면 **연결된 모든 통로**를 막는다 — 교차점이 뜨거우면 어느 방향으로도
지나갈 수 없기 때문이다.

### 경로 계층

- **벽 회피** — 도면에서 뽑은 벽(`extract-walls.py`)을 격자로 깔고 그 위에서 찾는다.
  직선으로 이으면 시각장애인이 벽으로 걸어간다. 통로는 실제 복도처럼 직각으로 꺾는다.
- **계단 하강** — 비상구는 도착이 아니라 반환점. 계단으로 1층까지 내려가야 완료.
  경사지 건물이라 지상이 두 군데인 경우도 다룬다.
- **엘리베이터 제외** — 화재 모드에서 언제나 뺀다. 도면 검증도 같은 기준이라,
  엘리베이터로만 닿는 방은 **고립으로 잡는다.**

### 건물 층 스택

관제가 한 층만 보여 주면 보는 사람에게 이것은 "한 층짜리 시스템"이다. 실제 건물은 7층에
옥상까지 있고, **대피는 층을 내려가는 일**이라 층이 안 보이면 대피가 안 보인다.

그렇다고 일곱 층을 다 "정상"으로 칠하면 안 된다. 도면을 안 올린 층은 아무것도 안 보고 있는데
화면은 보고 있다고 말하게 된다. 그래서 셋으로 가른다.

| 상태 | 뜻 |
|---|---|
| 감시 중 | 도면 + 감지기. 화면이 그 층을 실제로 본다 |
| 도면만 | 도면은 있고 감지기가 없다. 경로는 그리되 감지는 못 한다 |
| 도면 없음 | 아무것도 없다. 회색으로 두고 그렇게 적는다 |


제목은 증상을, 본문은 이유를 적는다. 무엇을 바꿨는지는 diff 가 말하므로 **왜 그렇게
해야 했는지**를 남긴다.

### 코드 리뷰

PR 단위로 본다. 이 프로젝트에서 리뷰가 특히 중요한 지점은 **"화면이 모르는 것을 아는 척하지
않는가"** 다. 기능이 도는 것보다 틀린 확신을 주지 않는 쪽이 우선이다.

## 6. 데이터·API 명세

### 데이터 구조

저장소는 인터페이스가 하나다 (`FirestoreRepo` | `MemoryRepo`). 라우터는 둘을 구분하지 않는다.

```
config/settings ──── activePlanId ────┐
                                      ▼
plans ─────────────┬──────────── planImages (1:1, planId)
  id (PK)          │
  name             │  nodes[]  ─── id · name · x · y · type · beaconId?
  metersPerUnit    │               type: room | junction | exit | elevator | stair
  stepLength       │
  northOffset      │  edges[]  ─── id · a · b · wall? · elevator?
  scaleEstimated   │               (a, b 는 nodes.id 참조)
  image {w,h}      │
  initialHazards   └─ edgeId → hazard
  draft · readConfidence · readEngine

hazards            edgeId (PK) → type · label · active · updatedAt · sensorId?
                   type: fire | smoke | heat | blocked | warm | crowd

sensors            sensorId (PK) → edgeId? | nodeId? · celsius · ts
                   (경로 계산 시점에 임계값으로 hazards 와 병합)

positions          userId (PK) → nodeId · nodeName · phase · confidence · x · y
                                 command · exitName · routeNodes[] · routeEdges[] · stepsLeft · ts
                   phase: idle | guiding | arrived | safehold

guardians          userId (PK) → name · contact · code (unique) · createdAt · updatedAt
                        │
alerts ─────────────────┘  userId · guardianName · phase · message · nodeName · exitName · ts

sos                userId · nodeId · nodeName · reason · confidence
                   guardianName · guardianContact (등록돼 있으면 자동 첨부) · ts

metrics            kind (initial|reroute) · ms · from · userId · found · ts
```

**관계**

- `plans.nodes[].id` ← `edges[].a/b`, `hazards.edgeId`, `sensors.edgeId|nodeId`, `positions.nodeId`
- `guardians.userId` ← `positions.userId`, `alerts.userId`, `sos.userId`
- `config.settings.activePlanId` → `plans.id` (활성 도면 하나)

**화재 중 데이터는 파일로 남기지 않는다.** 도면만 `backend/data/plans.json` 에 보존한다 —
사람이 그 건물까지 가서 찍은 것이라 재시작으로 사라지면 안 되고, 반대로 지난 화재가
다음 실행에서 되살아나면 안 되기 때문이다.

## 7. 보안과 배포

### 권한 경계

| 대상 | 권한 | 근거 |
|---|---|---|
| 위험 상태 쓰기 | **관제 토큰 필요** | 잘못된 위험 정보 주입은 곧바로 오안내 → 인명위험 |
| 도면 저장·활성화·삭제 | **관제 토큰 필요** | 활성 도면이 바뀌면 모든 사용자의 안내 기준이 바뀐다 |
| 도면 초안 접수 | **누구나** | 도면을 모으는 건 누구나 하는 일. 막으면 데이터가 안 쌓인다 |
| 위치·구조요청 보고 | **누구나** | 대피 중에 인증 절차를 요구할 수 없다 |

**"누구나 낼 수 있고, 확인은 담당자가 한다"** 가 도면 등록의 안전 경계다.
초안은 안내에 쓰이지 않고, 활성화만 관제 권한이다.

### 데이터 접근

프론트엔드는 Firestore 에 직접 접근하지 않는다. `firestore.rules` 가 **클라이언트 직접 접근을
전부 차단**하고, 백엔드만 Admin SDK 로 접근한다 (Admin SDK 는 규칙을 우회한다).
그래서 브라우저에 자격증명이 노출되지 않는다.

보호자 스트림은 `?code=` 로 **스코프가 좁혀진다.** 그 코드에 연결된 대상자의 위치·구조요청·
알림만 내려가고, 다른 대피자 정보와 운영 지표는 전달하지 않는다.
공유 코드는 **이미 쓰이지 않은 것으로 발급한다** — 겹치면 남의 대피 상황이 보이기 때문이다.

화면에 넣는 값은 이스케이프한다(`frontend/js/escape.js`). 지점 이름은 도면 판독이 만든 값이고
위치 보고는 인증 없이 들어오므로, 그대로 넣으면 관제·보호자 화면에서 남이 심은 스크립트가 돈다.

### 환경변수

```bash
# backend/.env
FIREBASE_PROJECT_ID=your-project-id          # 없으면 인메모리 모드로 동작
GOOGLE_APPLICATION_CREDENTIALS=./serviceAccountKey.json
ADMIN_TOKEN=아무_긴_문자열                    # 설정하면 관제 API 에 x-admin-token 필요

GOOGLE_API_KEY=...                           # 도면 판독 (둘 중 하나만 있으면 된다)
ANTHROPIC_API_KEY=...
DETECTOR_URL=http://127.0.0.1:8001           # 기호 탐지기 (꺼져 있어도 등록은 된다)
```

`ADMIN_TOKEN` 이 비어 있으면 통과시킨다 — 시연 편의를 위한 것이고,
**실서비스에서는 반드시 설정해야 한다.**

### 배포 구성

| 대상 | 위치 |
|---|---|
| 프론트엔드 | Firebase Hosting |
| 백엔드 | Cloud Run |
| 연결 | `firebase.json` 의 `/api/**` rewrite 로 같은 출처 유지 |
| 보안 규칙 | `firebase deploy --only firestore:rules` |

Firebase 설정이 없으면 인메모리 저장소로 뜬다. 실시간 전파·재탐색·구조요청까지 전부 동작하므로
시연에는 충분하다. Firestore 초기화가 실패해도 서버는 데모 모드로 계속 뜬다 —
시연 도중 자격증명 문제로 전체가 멈추는 상황을 피하기 위해서다.

## 8. AI 기능 명세

### 목적

피난안내도에는 비상구도, 현 위치도, 피난경로 화살표도 **이미 그려져 있다.** 없던 정보를
만드는 게 아니라, 그림으로만 있는 것을 **좌표로 옮겨 적는** 일이다.
지금까지 그 옮겨 적기를 사람이 클릭으로 했다 (도면 하나에 10분쯤).

### 처리 구조

두 모델이 각자 잘하는 것만 한다.

| 엔진 | 하는 일 | 못 하는 일 |
|---|---|---|
| **기호 탐지기** (자체 학습 YOLO) | 비상구·계단·실·문이 **어디 있는지** 상자로 집어낸다 | 글자를 못 읽고, 통로 연결을 모른다 |
| **언어모델** (Gemini · Claude) | 적힌 **이름**을 읽고 복도·화살표를 따라 **연결**을 판단 | 좌표는 눈대중이라 약하다 |

**좌표는 탐지기, 이름과 통로는 언어모델.** 한쪽만 있어도 동작한다.

| 구성 | 결과 |
|---|---|
| 둘 다 | 탐지기가 찍은 지점 위에 언어모델이 이름·통로를 얹는다 (가장 정확) |
| 탐지기만 | 지점은 정확, 통로는 기하학적 추정 + 이름은 번호 |
| 언어모델만 | 좌표까지 언어모델이 읽는다 (위치가 어긋날 수 있다고 경고) |
| 둘 다 없음 | 판독을 시작하지 않고 손으로 그리기로 넘긴다 |

```
사진 → 탐지기 (/detect) → 지점 상자
                              ↓
                        언어모델 (이름·연결)
                              ↓
                        sanitize (없는 노드 참조·범위 밖 좌표·중복 id 제거)
                              ↓
                        초안 저장 (draft: true) → 사람 확인 → 활성화
```

### 활용 기술

- **YOLO** 자체 학습 — 피난안내도로 라운드 반복 학습. 클래스별 담당 모델 라우팅 + 클래스별 NMS
  (`ml/detector/hybrid_detector.py`, 가중치·문턱·지표는 `models/class_router.json`)
- **FastAPI** 추론 서버 — `/health` · `/detect`. 별도 프로세스라 꺼져 있어도 본체가 안 죽는다
- **도구 호출(tool use)** — 언어모델이 정해진 스키마로만 답하게 강제. 자유 텍스트 파싱을 없앤다
- 학습 라운드별 기록은 `ml/README.md` 와 `ml/training-records/` 에

### 안전 장치

**사람 확인을 없애지 않는다.** 판독은 초안이다. 비상구를 하나 잘못 찍으면 시각장애인이
벽으로 걸어간다. 초안은 `draft: true` 로 저장되고 그 상태로는 활성화가 409 로 거부된다.
편집기에서 사람이 확인하고 저장해야 `draft` 가 벗겨진다.

**축척은 판독하지 않는다.** "1px 이 몇 m 인가"는 사진에 안 적혀 있다. 문 폭으로 어림할 수는
있지만 어림은 어림이다. 축척이 두 배 틀리면 "8미터 직진"이 16미터가 되고, 시각장애인은
그 걸음 수를 믿고 걷다가 모퉁이를 지나친다. **이 숫자 하나만은 사람이 직접 넣는다.**

**방위도 사람이 넣는다.** 도면이 실제로 어느 쪽을 향하는지는 그 앞에 서 있는 사람만 알 수
있어서, 앱이 촬영 직후 나침반으로 잰다.

**시야 점검이 먼저 돈다.** 게이트웨이를 거치면 이미지 블록이 조용히 버려질 수 있다. 그러면
모델은 그림을 못 본 채로 그럴듯한 도면을 지어내고 신뢰도까지 `high` 로 보고한다.
판독이 안 되는 것보다 **안 된 걸 모른 채 지어낸 경로를 저장하는 쪽이 훨씬 위험하다.**

판별법은 글자 인식이 아니라 **토큰 수 비교**다. 같은 질문을 그림을 붙여서 한 번, 안 붙이고
한 번 보내 `input_tokens` 를 견준다. 그림이 전달됐다면 반드시 늘어난다.
늘지 않으면 판독을 시작하지 않는다.

**모델이 형식을 지켜도 내용은 어긋날 수 있다.** 없는 노드를 가리키는 간선, 범위 밖 좌표,
겹친 id 를 걸러내고 **무엇을 버렸는지 경고로 사람에게 알린다.** 조용히 고치면 검수할 수 없다.

## 실행 방법

```bash
npm install       # 루트 + backend 의존성 (npm workspaces)
npm run dev:all   # 백엔드(:8080) + 프론트(:5173) 동시에, 죽으면 자동 재시작
```

| 실행 방식 | 명령 | 용도 |
|---|---|---|
| 한 번에 | `npm run dev:all` | 둘 다 띄우고 계속 살려 둔다 (시연용) |
| 프론트만 | `npm run dev` | :5173, `/api` 는 :8080 으로 프록시 |
| 백엔드 | VS Code F5 | :8080, 디버거 연결 |
| 백엔드 (터미널) | `npm run dev:backend` | 디버거 없이 자동 재시작 |
| 통합 1포트 | `npm start` | :8080 하나로 프론트까지 서빙 (배포 확인용) |
| 발표 문서 | `npm run docs` | :3030, `docs/` 정적 서빙 |
| 도면 탐지기 | `npm run detector` | :8001, 파이썬 YOLO 서버 (선택) |

프론트 개발 서버가 `/api/*` 를 백엔드로 프록시하므로 **같은 출처**가 되어 CORS 없이 SSE 까지
흐른다. `/shared/*` 는 사본이 아니라 원본을 직접 읽으므로 고치면 새로고침만으로 반영된다.

백엔드를 아직 안 띄웠다면 프록시가 503 을 돌려주고, 프론트는 오프라인 폴백으로 전환해
캐시된 도면으로 안내를 계속한다 — 이 동작 자체를 확인하는 용도로도 쓸 수 있다.

포트가 이미 쓰이고 있어도 개발 서버는 죽지 않는다. 이전 실행이 남아 있으면 그 사실을 알리고,
다른 프로그램이 점유했으면 다음 포트로 옮겨 뜬다. 직접 비우려면 `npx kill-port 5173`,
다른 포트를 쓰려면 `FRONTEND_PORT=3000 npm run dev`.

## 안전 고지

이 소프트웨어는 **모의대피 실험·UX 검증용 프로토타입**이며 재난안전 인증 제품이 아니다.
실제 화재 대응 용도로 사용해서는 안 된다.
